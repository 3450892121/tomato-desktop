# 文件藏图（工具：`imghide`）

> 范围：完整的文件打包 + 解包（纯离线），不做联网功能。
> 关键约定：
> 1. **目标是双向互通**：本工具打的图，外部「图夹」类网站 / APP 能解开；别人发来的图夹（含带密码的）本工具也能解开。
> 2. **同类工具并非天然互通**——只有实现同一套容器格式的才互通（LSB 隐写、「尾部拼 zip」之类与本项目格式互不相认）。
> 3. 外部图夹有**两套容器**，本工具两套都实现，且默认那套要与对方网站的判定一致：
>    - **动态混淆（极速）= 默认**：明文分隔符载荷（`DYNAMIC_V2_` + 随机分隔符 + base64 文件名 + 数据）**直接追加在图片尾部**，原版客户端靠全文件字节扫描定位，不解压、不弹密码框、多大文件都能开；
>    - **图夹 PRO（防查）**：`STEGDATA V6` 容器（PNG 塞进 IDAT 解压流 / GIF 尾部扩展块）+ 16 字节指纹 + 可选密码；原版客户端一看到指纹就弹「识别到图夹PRO文件」。
> 4. **不做联网功能**：网络图片解密、URL 转文件、图床、复制直链、生成图语一律不做——这些依赖对方服务器，属服务端能力；要分享就用对方网站上传。
> 5. 表图随机选择、可见水印不做（与互通无关，原版的默认水印只是叠字）。

## 目标
在工具箱里补上「把文件藏进图片 / 从图片里取出文件」这一能力，并与主流「图夹」实现**双向兼容**：
自己在电脑上打的图，朋友用网站或 APP 就能解开；朋友发来的图夹，本软件直接双击解开，不必再开浏览器。

## 范围

### 容器格式之一：动态混淆（极速，默认，原版「动态混淆(极速)」对位）

| 环节 | 规则 |
|---|---|
| 载荷 | `DYNAMIC_V2_` + 分隔符 + 每个文件 `分隔符filename分隔符 + base64(UTF-8 文件名) + 分隔符filename分隔符 + 分隔符file分隔符 + 原始字节` |
| 分隔符 | 随机串 + `|||`，**必须以 `|||` 结尾且整体长度 > 3**（原版从 `DYNAMIC_V2_` 之后取到第一个 `|||` 为止作为分隔符，写成 `|||xxxx|||` 只会取到 `|||`、长度 3、被判非图夹——实测踩过） |
| 隐藏位置 | 直接追加在图片**尾部**（表图原字节零改动，JPG/WebP/GIF 都行）；原版客户端拿整份文件字节扫描 `DYNAMIC_V2_`，所以放尾部最稳 |
| 密码 | 不支持（原版该模式也不支持） |
| 兼容 | 解析时同时支持更老的固定分隔符版（`|||ENCRYPT_DELIMITER|||` / `|||FILENAME_DELIMITER|||` / `|||FILE_DELIMITER|||`） |

### 容器格式之二：图夹 PRO（防查）

| 环节 | 规则（与原版 V6 一致） |
|---|---|
| 支持的载体 | **GIF 与 PNG** 两种（原版解包只认这两种） |
| 魔数 | `STEGDATA V6`（11 字节 ASCII），其前 3 字节固定 `21 FF 0B` |
| 载荷结构 | `uint32 文件数` + 每个文件 `uint32 名字长度 + UTF-8 名字 + uint64 大小 + 原始字节`（**不压缩**，大端序） |
| GIF 嵌入 | 原文件字节**零改动**，文件尾追加：`21 FF 0B` + 魔数 + 数据子块（每块 ≤255 字节，末尾 `00` 收尾）+ 指纹注释块 `21 FE 10` + 字节 `01..10` + `00`；载荷前带 4 字节大端长度前缀 |
| PNG 嵌入 | 把载荷拼到 **IDAT 解压流**（扫描线数据）尾部，再整体 zlib 重压成单个 IDAT，CRC 全部重算；末尾插 `iTXt(Software)` 指纹块（文本 = 字节 `01..10`） |
| 密码（原版称「图夹 PRO」） | PBKDF2-SHA256（密码 UTF-8 编码，**盐固定 `xcn2025`**，100000 轮，256 位）→ AES-256-GCM（12 字节随机 IV 前置，16 字节 tag 尾随） |
| 解包 | 按载体分流取载荷 → 有密码先解密（失败即「密码错误」）→ 解析文件表 → 落盘 |

### PNG 兼容性判定（原版解包按 `高 × (1 + 宽 × 每像素字节)` 切分隐藏数据）

| 表图情况 | 本工具处理 |
|---|---|
| 8 位深、非隔行（绝大多数 PNG） | **直接用原图字节**：不解码、不重压像素，只做 IDAT 手术 —— 画质零损失、体积最小 |
| 位深 ≠8 / 隔行扫描 / 调色板 <8 位 | 界面进程解码 → 画布重编码为 8 位 PNG（原版也是走 canvas 重编码），再做 IDAT 手术 |
| JPG / WebP / BMP 等 | 同上，输出统一为 PNG |
| GIF（含动图） | 原字节零改动，尾部追加扩展块 |

### 界面附带的便利功能（v2.5.0 起，与原版对齐）
- **随机表图**：画布生成装饰封面（渐变 + 光斑 + 细噪点，1024×1024），零素材零依赖、无版权问题；产物落系统「图片」文件夹（随机表图没有源目录）。
- **水印文字**（可选）：左上角白字 + 描边；填了会把表图重编码成 PNG 再写入（GIF 表图因此变成 PNG 产物，界面如实说明）。
- **算法选择**：与原版一致的两项（动态混淆（极速）/ 图夹 PRO（防查）），只有 PRO 才能设密码。
- **体积提示**：按模式区分——极速超大文件只提醒「微信传不动、建议网盘」；PRO 超大文件警告「网页版/手机多半打不开（要整张图解压，实测 788MB 需 2.3GB 内存）」。

### 非目标（本期明确不做）
- **不做任何联网功能**（前置结论 3）：网络图片解密、URL 转文件、图床、复制直链、图语。
- 不做「自研增强容器」模式：互通优先；将来若需要「超大文件/更强加密/只有本工具能解」再加，不影响本期格式。
- 不做「内置表图素材库」（随机表图改为程序生成，避免素材版权问题）；不做压缩（保持与原版逐字节一致最稳）。
- 不做「非图夹图片」的自动内容解密（本工具只认上面两套容器；其它隐写格式不猜）。

### 已知限制（如实写进界面）
- **微信/QQ 直接发图会把数据压没**（平台会重编码），必须「以文件方式发送」或压成 zip；贴吧要用原图链接。这与原版提示一致。
- 产物体积 ≈ 表图 + 里图（PNG 路径还会重建一次 IDAT，体积略有浮动）；原版建议保持 3MB 以内便于社交平台分享。
- 原版格式已迭代到 V6（历史上升过级）：若对方以后换 V7，兼容层会失效——届时跟进（格式逻辑集中在 `core/format.mjs`，改动面可控）。

## 界面
沿用工具箱既有形态与组件（`shell/components.css` 的 `card / btn / input / select / control-row`，颜色字号只用 `shell/theme.css` 变量）：
- **顶部模式切换**：`打包` / `解包` 两个分段按钮（同一工具页内切换，不新增工具）。
- **打包**
  - 表图卡：缩略图预览 + 文件名/尺寸/格式说明（GIF 原样追加；其它格式会转成 PNG）；`选择表图` / `清空`。
  - 里图卡：`添加文件`（任意类型、可多选）+ 拖拽入窗；列表显示名称/大小/移除；重复名自动提示。
  - 参数卡：密码（可选，对应原版「图夹 PRO」；可显示明文）。
  - 底部：`开始打包` / `清空` / 结果行（产物路径、体积、下一步提示）。
- **解包**
  - 图夹图片卡：`选择图片` / 拖拽；显示文件名与体积；密码输入框（带密码的图才需要）。
  - 底部：`开始解包` / `清空` / 结果区：解出文件列表（名称 + 大小）、`打开文件夹`、失败时给可读中文原因（「不是图夹图或图片已被压缩」/「密码错误」）。
- **拖拽**：打包页把图片拖进来当表图、其它文件当里图；解包页拖进来的图直接进解包位。全局交互均按 `ctx.isActive()` 让位。
- **提示行**：常驻一句「微信/QQ 请以『文件』方式发送，直接发图会被压缩导致数据丢失」。

## 主进程接线（`main.js`）
| 通道 | 入参 | 返回 |
|---|---|---|
| `imghide:pack` | `{ coverPath?, coverBytes?, coverKind:'gif'\|'png', items:[{path,name}], password?, outputDir?, jobId }` | `{ ok, path, size, ms }` |
| `imghide:unpack` | `{ imagePath, password?, outputDir? }` | `{ ok, dir, files:[{name,path,size}], encrypted, ms }` |
| `imghide:reveal` | `{ path }` | `{ ok }`（在资源管理器里定位） |
| `imghide:progress`（事件） | — | `{ jobId, percent, text }` |

- 产物不覆盖已有文件：`<表图名>_图夹.gif|png`，重名自动加序号（复用 `uniqueTargetPath`）。
- 解包默认落在 `<图片名>_解出/` 目录（重名加序号）；**条目名一律取 basename**，拒绝 `..`/绝对路径，防路径穿越；同时拦 **Windows 保留设备名**（`CON`/`NUL`/`COM1-9`/`LPT1-9` 等，含带扩展名形态，加 `_` 前缀避让）并剥掉结尾的点与空格（v2.8.1 起，对齐 Windows 落盘行为）。
- 专用对话框：`dialog:open-hide-cover`（图片，测试模式取夹具 `测试藏图表图*`）、`dialog:open-hide-files`（任意文件，测试模式取 `测试藏图文件*`）。

## 验收
- PNG 表图与 GIF 表图**双向**打包/解包逐字节一致（含中文文件名与 >4GB 以上的大小字段写法）。
- 密码：带密码打包 → 正确密码解开；错误密码给「密码错误」且不产出垃圾文件。
- 互通（关键项）：原版实现能解开我们打的图；我们能解开原版打法的图（含带密码）——两侧都逐字节一致。
- 兼容性判定：非 8 位/隔行的 PNG 与 JPG 表图会被重编码为 8 位 PNG，产物仍能互通解出。
- 图片本身仍可用：产物能被系统/画布正常打开，尺寸与原表图一致。
- 解包容错：非图夹图、被压缩过的图、损坏文件都给可读中文提示，不崩、不落空文件。
- 安全：条目名含 `..` 或绝对路径时拒绝写出（防路径穿越）。
- 文档：使用说明（面向使用者，含「以文件方式发送」的强调）。

## 关键事实来源
- 原版前端 **`https://tj.qdqqd.com/decryptWorker.js`**（69KB，**未混淆**的明文 JS）：类 `SteganographyCore` 中的 `extractDataFromGIF` / `extractDataFromPNG` / `streamPrepareEmbedData` / `streamEmbedDataInGIF` / `streamEmbedDataInPNG` / `encryptData` / `decryptData`，及常量 `STEG_DATA_V6`（`STEGDATA V6`）、`APP_EXT_MARKER`（`21 FF 0B`）、固定盐 `xcn2025`、PBKDF2 100000 轮 / AES-GCM 128 位 tag、PNG 切分公式 `height*(1+width*bytesPerPixel)`。
- 原版 `index.js`（经混淆）：图语格式 `^TJ_qdqqd_[a-zA-Z0-9]+$` → 拼 `CURRENT_DOMAIN` 取图，说明**图语是服务器短码**，离线无法生成。
- 原版帮助页自述「只能解密通过本工具加密的图片」→ 互通的前提是实现同一套算法。
- 许可与合规：本工具**按格式自行实现**，不复制对方代码；对方代码只作为**本机验证裁判**放在 `.tools/`（不进 git、不随包分发）。
